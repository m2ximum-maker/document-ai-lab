# Направление Проекта

Этот документ фиксирует не текущий pipeline, а продуктовую цель проекта: каким должен стать Smart Medical Archive и какие архитектурные решения помогают к этому прийти.

Техническая карта и команды запуска живут в [README.md](../README.md). Прогресс по шагам живёт в [PROGRESS.md](PROGRESS.md).

## Северная Звезда

Smart Medical Archive должен стать локальной системой, которая помогает семье помнить и собирать медицинскую историю по документам.

Не цель:

- заменить врача
- ставить диагнозы
- давать медицинские рекомендации

Цель:

- находить документы
- связывать документы с людьми и периодами
- извлекать важные metadata
- группировать историю по темам
- отвечать на вопросы с источниками

Коротко: система должна быть хорошей памятью по документам, а не медицинским авторитетом.

## Пользовательские Сценарии

Пользователь должен иметь возможность спрашивать не про имена файлов, а про медицинскую историю:

```text
Что мне говорил ЛОР?
Какие лекарства мне назначали от желудка?
Когда последний раз сдавал кровь?
Что было по щитовидке?
К каким врачам я ходил с марта по май 2026 года?
Что назначали питомцу?
```

Хороший ответ должен:

- собрать информацию из нескольких документов
- разложить её по датам или темам
- не смешивать владельцев документов
- показывать источники
- явно говорить, если данных не хватает

## Почему Нужна Каталогизация

Поиск по OCR-тексту видит фрагменты текста. Но медицинская история требует понимать документ как объект.

Документ должен постепенно получать структуру:

```text
owner: основной пользователь
doc_date: 26.12.2023
doc_type: выписка
doctor: ФИО врача
specialty: невролог
clinic: ...
```

Эта структура нужна для вопросов вроде:

- какие документы были в 2026 году
- какие врачи встречались в периоде
- какие анализы относятся к одному владельцу
- какие документы относятся к ЖКТ, ЛОР, крови или лекарствам
- какие источники подтверждают ответ

## Роль SQLite

SQLite — это структурированная память архива.

Он хранит не embeddings, а факты о документах:

- владелец
- дата документа
- тип документа
- врач
- специальность
- клиника
- путь к исходному тексту
- статус извлечения metadata
- уверенность извлечения

Chroma и SQLite не конкурируют:

- Chroma помогает найти релевантные chunks по смыслу.
- SQLite помогает отфильтровать, сгруппировать и объяснить найденное.

Иначе говоря, Chroma отвечает на вопрос “где похожий текст?”, а SQLite — “что это за документ и к какой истории он относится?”.

## Сохранение Текущего RAG

Текущий RAG pipeline уже является рабочей частью проекта, и его не нужно переписывать ради SQLite.

Существующий flow сохраняется:

```text
output/cleaned/*.txt
↓
src/chunk.py
↓
output/chunks/chunks.jsonl
↓
src/embed.py
↓
Chroma
↓
src/search.py
↓
src/ask.py
```

SQLite Catalog добавляется сначала как соседняя ветка:

```text
output/cleaned/*.txt
├── src/chunk.py -> chunks.jsonl -> Chroma -> search/ask
└── src/catalog.py -> SQLite
```

На первых шагах `search.py` и `ask.py` не меняются. Интеграция с RAG возможна позже, только маленькими изменениями: например через optional filters или candidate document ids перед retrieval.

Старый режим поиска и `ask.py` должен оставаться рабочим даже после появления каталога.

## Metadata Extraction

Metadata extraction будет отдельным слоем после OCR.

Владельцев документов нужно нормализовать с учётом приватности. Реальные имена хранятся только локально в приватном словаре, который не попадает в git. В metadata и будущий каталог должны попадать стабильные псевдонимы вроде `person_1`, `person_2`, `cat_1`, а не реальные имена членов семьи или питомцев.

На первом этапе значения могут быть простыми:

- `owner = unknown`
- `doc_type = unknown`
- `doc_date = null`

Позже LLM/regex смогут извлекать:

- `owner`
- `doc_date`
- `doc_type`
- `doctor`
- `specialty`
- `clinic`
- `confidence`
- `extractor`
- `extracted_at`

Важно не спешить с “умной” extraction: сначала нужен устойчивый каталог документов, потом можно добавлять извлечение metadata и проверять качество на реальных примерах.

## Как Обрабатывается Вопрос Пользователя

Пользовательский prompt не должен напрямую превращаться в SQL.

Вместо этого система должна строить маленький проверяемый query plan:

```text
user prompt
↓
intent + filters
↓
safe SQL template
↓
SQLite rows
↓
optional Chroma chunks
↓
compact LLM context
↓
answer with sources
```

Например вопрос:

```text
К каким врачам я ходил с марта по май 2026 года?
```

можно превратить в план:

```text
intent: list_doctors
owner: current_user
date_from: 2026-03-01
date_to: 2026-05-31
needs_chunks: false
```

SQL при этом берётся из заранее написанного шаблона, а не генерируется свободно:

```sql
SELECT doc_date, doctor, specialty, clinic, doc_type, source
FROM documents
WHERE owner = ?
  AND doc_date BETWEEN ? AND ?
  AND doctor IS NOT NULL
ORDER BY doc_date;
```

Параметры передаются отдельно:

```text
current_user, 2026-03-01, 2026-05-31
```

Так проще отлаживать поведение, контролировать приватность и не давать LLM произвольно читать всю базу.

## Когда Нужны Chunks

Не каждый вопрос требует Chroma.

Если ответ лежит в metadata, можно отвечать по SQLite:

- к каким врачам я ходил
- какие документы есть за период
- когда была последняя эндоскопия
- в каких клиниках я был
- сколько анализов крови есть за год

Если ответ лежит внутри текста документа, нужны chunks:

- что мне назначали
- что врач написал в заключении
- какие были рекомендации
- что было по желудку
- были ли жалобы на боль

В таких случаях SQLite сначала сужает набор документов по владельцу, датам, типу или врачу, а Chroma ищет релевантные фрагменты только внутри подходящего набора.

## Что Получает LLM

LLM не должна получать всю SQLite-базу и все chunks.

Она получает только компактный context, собранный под конкретный вопрос:

```text
Вопрос пользователя:
К каким врачам я ходил с марта по май 2026 года?

Найденные документы:
- 2026-03-14, консультация, врач: ФИО врача, специальность: ЛОР, источник: source1.txt
- 2026-04-02, заключение, врач: ФИО врача, специальность: гастроэнтеролог, источник: source2.txt

Инструкция:
Ответь только по найденным данным. Если данных мало, скажи об этом.
Укажи источники.
```

То есть SQLite и Chroma используются до LLM как фильтры и источники фактов. LLM формулирует ответ, но не должна сама решать, какие таблицы или документы читать.

## Архитектурные Границы

Ближайшая цель — добавить SQLite Catalog рядом с текущим flow.

На этом этапе не нужно:

- переписывать весь pipeline
- переписывать текущий RAG
- менять `chunk.py`
- менять `search.py`
- менять `ask.py`
- менять формат `chunks.jsonl`
- мигрировать Chroma
- делать LLM metadata extraction

Главный принцип: маленькие понятные шаги, которые легко ревьюить.

## Вопросы На Будущее

Эти решения лучше принимать позже, когда появится больше документов и примеров:

- какие поля должны быть колонками в `documents`
- какие metadata лучше хранить в отдельной таблице
- как хранить confidence по каждому полю
- как связывать `documents` и chunks
- как нормализовать врачей, клиники и специальности
- как отличать пациента, владельца файла и автора документа
- как показывать источники на уровне документа, страницы и chunk
